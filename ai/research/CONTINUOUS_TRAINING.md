## 启动、查看、停止

```bash
npm ci
python -m pip install -r ai/environment/requirements-training.txt
npm run train:continuous
```

默认运行目录是 `ai/danMCai/runs/main`（已被 Git 忽略）。常用参数：

| 参数                | 作用                                                   |
| ------------------- | ------------------------------------------------------ |
| `--run=<目录>`      | 运行目录；同一目录再次启动即断点续跑                   |
| `--hours=<小时>`    | 运行时长上限，`0` 表示一直运行                         |
| `--config='<JSON>'` | 仅首次启动时覆盖默认配置，之后配置冻结在 `config.json` |
| `--python=<命令>`   | 训练进程使用的 Python，默认 `python`                   |

例如用 8 个采样进程、把整场结果按一半权重计入目标：

```bash
npm run train:continuous -- --run=ai/danMCai/runs/match-half --config='{"actors":8,"learner":{"targetMatchWeight":0.5}}'
```

查看进度：

```bash
npm run train:status
npm run train:status -- --run=ai/danMCai/runs/match-half
```

### 实时进度面板

```bash
npm run train:dashboard
```

打开 [danMCai 训练进度](http://127.0.0.1:8766/)，也可把此地址放在 Codex 的右侧浏览器面板。页面每 5 秒读取真实状态，显示当前交接步骤、运行时间、整场采样数、学习决策、全网络更新步数、进程状态、最近保存模型、门控冠军、进行中的对战检查及报告发布状态。

时间进度条仅表示本次运行时限的完成比例，不能解释为棋力、胜率或整个交接的完成比例；完成一次训练也不会自动把后续步骤标为已完成。采样数据与开发门控均不等于独立验收。状态过期、进程退出或连接中断时页面会提醒，最后记录不会被显示成持续训练的证明。

面板是独立的只读本机服务，默认端口 8766，只监听 `127.0.0.1`，不访问任意文件、不提供训练修改接口，不随 GitHub Pages 发布。关闭面板不停止训练；若电脑重启或服务退出，重新运行上述命令即可。可用 `--run=<目录>`、`--port=<端口>` 指定其他运行和端口。

停止：在运行窗口按 Ctrl+C，或在运行目录里新建一个名为 `STOP` 的文件。各进程会结束当前比赛、保存检查点后退出；再次执行同一命令即从断点继续。

需要开机后自动续跑时，可用 Windows「任务计划程序」新建任务：触发器选「登录时」，操作为在仓库目录执行 `npm run train:continuous`。

## 结构

```text
 采样进程 ×N（Node + onnxruntime-node，每进程 1 线程）
   每场开始读取最新模型；按比例选择对手：
     自对弈（四席最新模型）／联赛池（按 PFSP 抽取）／规则机器人
   按探索规则选牌，按整场写出 int8 样本分片
        │ shards/*.x.i8 + *.y.f32 + *.json
        ▼
 训练进程（Python + PyTorch）
   最新若干百万行的重放缓冲区 → 回归 Q(o,a) 到蒙特卡洛回报
   每隔若干分钟导出 ONNX → models/latest.json
        │
        ▼
 调度进程（supervisor）
   崩溃重启、汇总对局结果（PFSP 统计）、定时把最新模型存入联赛池、
   按候选调度选择快照启动门控：与当前冠军配对对局，SPRT 判定是否更替冠军
```

## 新快照优先的门控调度

历史默认行为仍会从联赛池逆序寻找未测候选；没有 `gateSchedule` 的旧运行保留该行为。所有者授权本次 Mac 切换为 `new-first-v1`，通过正常保存、新冻结检出和具名 `--protocol-change`／`--set` 应用，当前参数和恢复命令以 [MAC_HANDOFF](MAC_HANDOFF.md) 为准。

- `minNewStep` 固定切换保存点，`activatedAt` 固定首次启用时间；切换立即快照一次，以后沿用原快照间隔。仅最新一份合格快照进入门控，较旧的待测快照不补赛，普通恢复不重设边界。
- `historicalChampions` 为 0–2，按真实冠军历史选择最近几位前冠军，排除 P0 和现任。`historyIntervalHours` 至少 1 小时，本次为 3 小时；最近一次历史挑战启动时间持久保存，重启不重置限频，同一候选／现任冠军的完整门控不重复。
- 有新候选时优先新候选；无新候选且历史检查未到期时空闲。已开始的门控正常完成；原到期 P0 锚点优先启动，检查间隔、150 对、置信区间和两次退步停机规则不变。
- 这只改变候选选择。训练对手池、奖励、Adam、样本、牌规、SPRT 和种子区间沿用原值。跳过没有评测的快照不写成 reject；中断报告不拼入完整结果，不把空闲时间等同于已测得的吞吐提升。

回归覆盖见 `ai/danMCai/tests/gate-schedule.test.mjs` 与 `continuous-training.test.mjs`；`npm test` 同时检查新快照优先、停止补赛、历史限频、候选／冠军配对和协议参数边界。

## 局域网内另一台电脑一起采样

训练进程、门控和联赛池只在运行调度进程的主电脑上；另一台电脑只跑**采样进程**，从共享文件夹读最新模型、把样本分片写回同一个运行目录。显卡训练常常在等 CPU 打牌，多一台电脑的 CPU 能直接增加数据量。

### 主电脑

1. 正常启动运行，例如 `npm run train:continuous -- --run=ai/danMCai/runs/gpu-main`。
2. 在资源管理器里右键运行目录（例如 `D:\vibecoding\guandan\work\continuous\gpu-main`）→「属性」→「共享」→「高级共享」，勾选「共享此文件夹」，在「权限」里给另一台电脑登录用的账户「更改」和「读取」权限。
3. 记下共享路径，例如 `\\主电脑名\gpu-main`。

### 另一台电脑

1. 安装 Node.js 20.19 以上；不需要 Python，也不需要显卡。
2. 克隆仓库，切到**与主电脑运行时相同的提交**，执行 `npm ci`。启动器会按运行配置里冻结的代码指纹逐个核对，不一致就拒绝启动。
3. 把共享文件夹映射为盘符（资源管理器 →「此电脑」→「映射网络驱动器」），例如 `Z:`。
4. 启动采样，编号选主电脑没用的槽：主电脑占用 `0` 到 `actors-1`（`gpu-main` 是 0–7），可用范围到 39。一般每个 CPU 核心一个，留一两个核心给系统：

```bash
npm run train:remote -- --run=Z:/ --slots=8-13
```

### 启动器做什么

- 拒绝主电脑自己的槽，以及另一台电脑在 3 分钟内还在使用的槽（`actors/claim-<槽>.json` 记录占用的电脑名和心跳）。
- 采样进程崩溃或网络中断后按退避重启；主电脑创建 `STOP` 时等待，调度进程恢复后自动继续。
- 每个槽有独占的种子区间，并沿用运行配置的 `actorSeedOffset`，两台电脑不会打重复的牌局。
- 事件写入 `actors/remote-<电脑名>.jsonl`，记录电脑名、槽、代码提交与重启原因。
- 按 Ctrl+C 只停这台电脑。尚未写出的分片（最多一个 `shardSeconds` 间隔）会丢弃；被强制结束时占用记录会留下，3 分钟后失效，同一台电脑可以立即重新占用。

### 统计口径

调度进程的 `status.json` 只统计本机槽。`npm run train:status`、实时面板与 `ai/research/tools/update-model-study.py` 改为汇总运行目录里全部 `actor-*.json`，报告另记 `actorSlots`、`remoteActorHosts` 和 `supervisorLocalTotals`，所以远程打的比赛会计入实际完成场数。联赛 PFSP 统计和训练进程本来就读取全部采样槽的结果与分片。

不要用 OneDrive 等网盘同步代替共享文件夹：网盘可能先同步清单、后同步数据，训练进程会把未传完的分片当作坏分片丢弃。

## 快速采样进程（GPU 批量推理）

标准采样进程（`actor.mjs`）一次只打一局，每个决策在 CPU 上单独推理。剖析一个标准进程的自对弈，主线程时间约 48% 花在模型推理、38% 在出牌候选生成、5% 在编码；规则机器人对局中规则机器人约占 12%。

`fast-actor.mjs` 做三件事：

1. **一个进程同时打几十局**（默认 48 局），把这些局等待中的决策按 24 个一组交给 GPU（DirectML，`onnxruntime-node` 自带），GPU 不可用时自动退回 CPU。
2. **推理放在独立线程**（`inference-worker.mjs`），主线程把一组交出去后继续推进其他对局，不等 GPU。
3. **候选生成缓存**（`fast-candidates.mjs`）：同一手牌的出牌全集只算一次，跟牌时按能否压过上家筛选。原生成器先按牌型生成、再逐个判断能否压过，生成顺序与上家无关，所以结果和顺序与原来完全一致。

对局逻辑用 `fast-rollout.mjs`：它是 `ai/shared/simulation/match-rollout.mjs` 的副本，唯一改动是可以传入候选生成函数。模型改成逐行批量输入由 `onnx-rows.mjs` 在内存中改写 ONNX 输入维度完成，不需要 Python。样本分片、状态文件、对局结果、种子区间、探索规则和标签都与标准进程相同，只多记 `actorImplementation: "fast"` 和推理设备。

**已验证**（机器可读记录见 [fast-actor-throughput-2026-11-05.json](./evaluation/fast-actor-throughput-2026-11-05.json)）：

- 39,959 个真实决策上，缓存候选与原生成器逐一相同；候选生成快约 1.29 倍。
- 8 场比赛中，副本对局流程与原版输出完全相同。
- GPU 批量推理与 CPU 推理在 300 个局面上的最大误差约 4×10⁻⁶，最优出法全部相同。因此快速进程在规则和策略上等价，但采样到的动作不保证逐位相同。
- 吞吐：本机在 `gpu-main` 同时运行时，4 个进程预热 90 秒后计 210 秒，标准进程合计 1,220 决策/秒，快速进程 2,530 决策/秒，约 2.07 倍。这是共享负载下的单次测量，不是独立的硬件极限，也不代表棋力提升。

**怎么用**：调度进程目前只会启动标准进程（它属于运行冻结的源码，运行期间不能改）。用远程启动器在**本机或其他电脑**上启动快速进程，槽号必须不小于运行配置的 `actors`：

```bash
npm run train:remote -- --run=ai/danMCai/runs/<运行名> --slots=8-11 --actor=fast --games=48
```

- 想让一次新运行主要使用快速进程，可以首次启动时设 `"actors": 1`，再用上面的命令为槽 1 起启动快速进程。
- 往**正在运行**的训练里加入快速进程属于协议变化：要在研究报告里写明加入的时间、槽号和实现，不能把前后数据当作同一协议。
- 本机 CPU 被占满时，快速进程会和标准进程抢 CPU；最好用快速进程替换标准进程，而不是在上面叠加。

## 训练目标

### 显卡训练（AMD ROCm / CUDA）

学习器默认使用 CPU。显卡运行需要对应的 PyTorch 环境；AMD ROCm 同样使用 `cuda:0` 设备接口。本机已经验证 RX 7800 XT 可用，GPU 环境位于 `D:\vibecoding\guandan\work\gpu-runtime\Scripts\python.exe`。该环境从本机已有的 Python 3.12 ROCm 安装创建，不要用 CPU 版 `ai/environment/requirements-training.txt` 覆盖其中的 PyTorch。

```bash
npm run train:continuous -- --run=D:/vibecoding/guandan/work/continuous/gpu-main --hours=24 --python=D:/vibecoding/guandan/work/gpu-runtime/Scripts/python.exe --config='{"actors":8,"actorSeedOffset":1000000,"evaluationBlockOffset":100,"learner":{"device":"cuda:0","threads":1}}'
```

此示例应在最新 `main` 源码执行，实际主工作目录为 `D:\vibecoding\guandan`。原纯 CPU 基线已按用户要求暂停，采样与学习进程均退出，旧检查点和证据保留；它未运行满 24 小时，不算交接第 1 步已经完成。当前 GPU 主运行使用上述绝对路径，报告器能同时看到旧结果和新进展。运行中的 `config.json` 不得改写；更换后端须开新运行目录。显卡不可用会报错，不以 CPU 冒充 GPU。CPU 仍负责为 GPU 生成自对弈牌局与执行规则。

`actorSeedOffset` 默认 0，在各采样槽的训练种子块内设置起点；恢复仍优先使用保存的下一种子。`evaluationBlockOffset` 默认 0，只改变首次分配的门控／锚点块序号，后续持久化和耗尽保护不变。这两个偏移不改变训练、门控、锚点及留出的用途边界。

进度面板和 `npm run train:status` 在本机存在 `ai/danMCai/runs/gpu-main/config.json` 时优先查看 GPU 主运行，可用 `--run` 覆盖。面板显示设备名称、实际场数、更新次数与已暂停 CPU 基线。每 5 秒请求最新状态，场数直接聚合各采样进程逐场写入的计数；学习器状态在训练时约每 10 秒、等待样本时约每 2 秒更新，调度心跳约每 30 秒更新，二者不混为面板刷新时间。保存模型仍约每 10 分钟一次。设备短测见研究报告第 7.9 节；约 10.12 倍是不同运行库下训练计算的短测比值，初期端到端观测约为 1.32 倍（第 7.11 节），尚不能推断长期效率和棋力提升。

网络结构与网页的 P0 完全相同（$567\to512\times5\to1$），导出的 ONNX 与 `ai/danMCai/models/baseline/policy.onnx` 使用同一输入输出，网页 Worker 和 `npm run eval:table -- --policy=<文件>` 都能直接加载。

每条样本保存四个目标分量：本局升级分（本队 +1～+3 或对方 −1～−3）、整场结果（+1／−1／平局 0）、局序号、整场局数。训练目标为

$$
G = (1-w)\cdot\text{本局升级分} + w\cdot 3\cdot\text{整场结果},
$$

$w$ 即 `targetMatchWeight`，默认 0，即延续 P0 原有的单局升级分尺度；改变 $w$ 不需要重新采样。损失为 $(Q_\theta(o,a)-G)^2$，可选对初始模型输出的保持项 `anchorWeight`。

## 探索规则

`exploration` 可取 `{"type":"softmax","temperature":T}`、`{"type":"epsilon","epsilon":ε}` 或 `{"type":"greedy"}`。默认 softmax T=0.02 来自一次开发测量：探索方与贪心对手都是 P0，150 对种子、300 场，平局记 0.5。

| 规则           | 平均得分 | 非贪心决策占比 |
| -------------- | -------: | -------------: |
| 贪心（对照）   |    0.500 |             0% |
| ε=0.01 均匀    |    0.422 |           0.8% |
| softmax T=0.02 |    0.517 |          10.3% |
| softmax T=0.05 |    0.357 |          19.1% |

均匀探索偶尔随机打出炸弹或拆牌，代价约 8 个百分点；T=0.02 的 softmax 只在分数接近的出法之间探索，在这个样本量下看不出代价。每组约有 ±6 个百分点的不确定性，只用于选择默认值。复现：

```bash
node ai/danMCai/training/continuous/explore-cost.mjs --pairs=150 --exploration='{"type":"softmax","temperature":0.02}'
```

## 种子与数据用途

研究报告迄今使用的开发与留出种子都小于 1e9。持续训练的采样种子从 1,000,000,000 起，每个采样进程独占 5,000 万个；探索测量从 3,400,000,000 起；门控种子从 3,500,000,000 起，每次门控独占 10 万个。门控和监控对局都属于开发用途，不能当作留出验收。

门控使用区间 [3,500,000,000, 3,600,000,000)，锚点独占 [3,600,000,000, 3,700,000,000)，每次检查占用 100,000 个种子的块，实际只运行配置要求的前缀。块序号在启动检查前持久化，恢复后不重用本运行已经分配的块；区间耗尽即报错，不回绕。不同开发运行可重用开发种子，但它们不构成独立留出证据。

锚点双方均贪心出牌，不启用网页性格、残局搜索或直接出完捷径；每个种子交换阵营各打一场。胜记 1、平记 0.5、负记 0，按两个结果的种子簇均值计算双侧 95% Hoeffding 区间。只有完整 150 对才计入连续退步；不完整或恢复到阈值以上会重置连续计数。每次区间是单次检查的界限，没有校正长期反复监控的整体误报率。

运行首次启动时记录训练、模拟与编码源码的 SHA-256（文本按 LF 规范化）。重启或运行期间发现源码变化会停止，须换新运行目录；不要修改既有 `config.json` 绕过协议检查。累计运行时间跨恢复累加，不含暂停时间。`STOP` 导致的正常退出不会触发崩溃重启。

## 给日常使用预留内存

快速采样现在采用有界资源：每个推理线程串行运行原生批次，最多缓存 6 个模型会话，逐次等待淘汰会话释放；单次原生推理最多 4,096 行，大候选列表分块完整评分，不截断合法动作。输入／输出张量用完即释放，关闭 CPU arena 与 memory pattern；候选缓存从 4,096 手降为 512 手。上述都是工程实现变化，不能当作棋力提升证据。

调度器每 5 秒检查系统可用内存：低于 4 GiB 时让一个快速采样器结束当前比赛、落盘后暂停；高于 5 GiB 再逐个恢复，同类操作至少间隔 20 秒。这是有滞后的软预算，结束比赛需要时间，不保证任何瞬间都严格空闲 4 GiB。暂停状态及可用内存显示在面板。学习器与采样器使用 BelowNormal 优先级，让普通桌面程序优先；不通过清空操作系统缓存或删训练数据腾内存。

Mac 真机启动后修正可用内存口径：`vm_stat` free + inactive 页用于预算，原始空闲页与测量方法分别留档；读取失败保守使用原始空闲量并记录错误。Windows 仍使用原有系统空闲内存。Mac 固定窗口中的兼容性修复及具名恢复流程见 [MAC_HANDOFF](MAC_HANDOFF.md)，恢复不延长截止时间。

配置记录在 `config.resourceBudget`。同一运行调整采样进程数、并行牌局或资源预算时，须先正常停止并保存，用 `--protocol-change=<实际原因>` 和 `--set` 显式记录，不能偷偷改冻结配置。比如 `--set='{"actors":8,"fastActor":{"games":8,"provider":"dml"},"resourceBudget":{"reserveGB":4,"resumeGB":5}}'`。该入口仍拒绝更改学习率、探索和奖励定义。

`gpu-main` 本次发生过内存耗尽，正常保存到 212,171 步，随后恢复原权重、优化器、缓冲区及种子游标。8×48 牌局的有界缓存方案减少了内存，但存在模型加载抖动，已改为 8 个进程、每进程 8 局，用户最后指定预留 4 GiB；提高有界会话缓存至 6 以减少反复加载。各阶段实际测量见研究报告第 7.13 节，不把中断前后当作独立棋力实验。
