### 实测过的数字

全部来自本机（Ryzen 7 7800X3D，16 线程，32 GB，CPU）：

| 项目                           | 结果                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------ |
| 单线程推理，P0 图              | 浏览器 WASM 约 1.0–1.2 万候选/秒；原生 `onnxruntime-node` 约 4.2–4.6 万候选/秒 |
| 单个采样进程                   | 完整自对弈约 620–660 决策/秒，推理约占六成                                     |
| 3 个采样进程同时运行           | 合计约 1,430–1,610 决策/秒                                                     |
| 训练进程（4 线程，batch 2048） | 约 2.3 步/秒，约 4,800 行/秒                                                   |
| 门控                           | 16 场整场约 12–20 秒                                                           |
| 导出往返                       | 载入 `ai/local/models/baseline/policy.onnx` 再导出，ONNX 输出逐位一致          |

探索规则代价（`explore-cost.mjs`，种子 3,400,000,000 起，150 对、300 场；探索方与贪心对手为同一个 P0；平局记 0.5）：

| 探索规则       | 平均得分 | 非贪心决策占比 |
| -------------- | -------: | -------------: |
| 贪心（对照）   |    0.500 |             0% |
| ε=0.01 均匀    |    0.422 |           0.8% |
| softmax T=0.02 |    0.517 |          10.3% |
| softmax T=0.05 |    0.357 |          19.1% |

据此把默认探索从 ε=0.01 改为 softmax T=0.02：探索量多一个数量级，而在这个样本量下看不出代价。这是开发测量，每组约 ±6 个百分点的不确定性，只用于选默认值。

端到端冒烟（3 个采样进程、缩小的参数，12 分钟）：2,101 场整场、0 场出错、981,053 个决策、训练 1,867 步、6 次门控，到时限后正常停机。冒烟结束的模型 v000001867 与初始 P0 贪心对局 150 对：126 胜、147 负、27 平，平均得分 0.465，95% 区间 [0.419, 0.511]，**没有显著差别，点估计偏低**。12 分钟的训练本来看不出效果，但长期运行时一定要盯住「对初始模型」这一项（第 1 步）。记录见 [ai/research/evaluation/continuous-smoke-2026-11-04.json](./evaluation/continuous-smoke-2026-11-04.json)。

**局域网采样机**：`npm run train:remote -- --run=<共享运行目录> --slots=8-13` 让同一局域网的另一台电脑只跑采样进程，样本写回主机运行目录，训练和门控仍在主机。启动器核对冻结代码指纹、防止槽冲突、断线重启；报告、状态命令和面板已改为统计全部采样槽。只做过同机模拟测试，详见[持续训练指南](./CONTINUOUS_TRAINING.md#局域网内另一台电脑一起采样)。注意：远程电脑必须检出与主机运行相同的提交，否则会被拒绝；`gpu-main` 冻结的源码文件不能改动，远程启动器本身不在冻结列表里。

**快速采样进程**：`fast-actor.mjs` 一个进程同时打 48 局，GPU（DirectML）批量推理放在独立线程，并缓存候选生成；同条件下 4 个进程约为标准进程的 2.07 倍（1,220 → 2,530 决策/秒），与原版的等价性已验证，详见[持续训练指南](./CONTINUOUS_TRAINING.md#快速采样进程gpu-批量推理)。调度器属于 `gpu-main` 冻结源码，目前只能用 `npm run train:remote -- --run=<运行目录> --slots=<槽> --actor=fast` 启动。**建议**：`gpu-main` 结束后，在新运行开始前给 `supervisor.mjs` 加一个配置项（例如 `actorImplementation: "fast"`），让调度器直接启动快速进程，再开新运行；不要在 `gpu-main` 运行期间修改冻结文件。若要往 `gpu-main` 中途加入快速进程，先征得用户同意，并在报告中作为协议变化记录。

**`gpu-main` 现在的运行方式（2026-11-05 起）**：

- 已于 03:56:54Z 在同一运行目录续跑，调度器的 8 个采样进程全部换成快速进程（`actorImplementation: "fast"`，每进程 48 局，DirectML）；权重、优化器、样本、联赛池、冠军和计数都接着原来的，这次协议变化记录在 `config.protocolHistory` 和研究报告第 7.12 节。
- 调度器、采样、训练和面板都从**独立运行目录 `D:/vibecoding/guandan-runtime`**（`git worktree`，分离检出）启动，不再从项目根目录启动。不要删除这个目录；更新它之前，先确认新提交没有改动 `config.json` 里 `sourceSHA256` 列出的任何文件，否则调度器会因源码变化停机。
- 续跑脚本是 `ai/local/runs/resume-gpu-fast.mjs`；启动记录在运行目录的 `launcher.json`（`restarts` 字段）。
- 不要再额外加快速进程：12 个快速进程时显卡被推理占满，训练降到约 2 次更新/秒；8 个时训练最快。若要再提速，方向是把所有采样进程的推理集中到一个进程里批量提交，减少和训练进程争用显卡。

### 第 1 步：启动长期运行，接入报告

**目标**：让系统一直跑，结果自动进研究报告。

1. 用默认配置启动：`npm run train:continuous -- --run=ai/local/runs/main`。运行至少 24 小时。
2. 扩展 `ai/research/tools/update-model-study.py`：读取 `<run>/status.json`、`<run>/gate/*.json`、`<run>/champion/champion.json`，把以下内容写进第 11 节生成区和 `ai/research/evaluation/model-study-progress.json`：
   - 运行时长、采样场数、决策数、训练步数；
   - 每次门控的挑战者、冠军、对数、胜／负／平、LLR、结论；
   - 冠军更替历史和模型 SHA-256。
3. 在 `supervisor.mjs` 里加「锚点检查」：每隔几小时，用 `gate.mjs` 让最新版本和 `models/anchor.onnx`（初始 P0）贪心对局固定 150 对（`--settings='{"minPairs":150,"maxPairs":150}'`，种子另划区间），记录平均得分和区间。连续两次区间上限低于 0.5 时，自动停止并在 `events.jsonl` 写明原因。之后可以考虑调低学习率，或者把 `anchorWeight` 设为大于 0 再开新运行。
4. 在 `ai/research/tests/model_study_test.py` 和 `ai/local/tests/continuous-training.test.mjs` 里加对应测试。

**完成标准**：第 11 节能显示持续运行的门控记录和锚点检查；全部注明是开发集；测试通过。

### 第 2 步：锁定留出种子，写冠军验收脚本

**目标**：用固定流程判断冠军是否有独立棋力提升证据；所有者授权的定期网页部署与此验收分开。

1. 选一段从没用过的种子作为留出集，例如 `900000000` 起 2,000 个。在 `ai/research/evaluation/` 新建一个 JSON，记录区间、用途和提交时间；提交后不再改动。
2. 新建 `ai/local/training/continuous/accept.mjs`，调用 `ai/local/evaluation/evaluate-table.mjs` 的同一套逻辑：
   - 冠军 vs 当前网页默认模型，配对种子、交换阵营，五种风格都跑；
   - 冠军 vs 规则机器人；
   - 输出逐种子结果、胜／负／平、按种子聚类的 Hoeffding 区间和 SHA-256。
3. 每次用过的留出种子要记录下来，同一段种子只能用于一次最终决策。

**完成标准**：脚本能对一个冠军文件跑完并产出报告；文档写明判定规则（事先定好的单侧下界）；没有修改网页模型。

### 第 3 步：门控并行化

**目标**：门控速度跟上快照频率。

- 门控进程开 K 个工作进程，按种子对分配，结果汇总后再做 SPRT；
- 注意 SPRT 的停止判断只能在汇总后做，不能由单个工作进程决定。

**完成标准**：4 个工作进程时门控吞吐至少提高 3 倍；结论和单进程时用同样种子、同样顺序得出的结论一致（写一个测试）。

### 第 4 步：整场目标（势函数塑形）

**目标**：从单局升级分过渡到整场胜率，同时不增加方差。

1. 用采样进程的 `results-*.jsonl` 和比赛历史，估计整场局面胜率表 $V(\text{双方级数}, \text{打 A 失败次数}, \text{当前打哪方的级})$，写成脚本，产出 JSON。
2. 在 `learner.py` 增加目标选项：每局奖励 $V(s') - V(s)$（基于势函数的塑形）。
3. 用同一初始模型、同样采样设置，各开一个运行目录比较 `targetMatchWeight=0`、`0.5` 和势函数版本，对比门控记录。

**完成标准**：三个运行都至少跑够同样的训练步数；结果（包括负结果）写进研究报告第 7 节；默认值只有在证据支持时才改。

### 第 5 步：对全部候选的约束

**目标**：避免第 4.2 节记录的「验证误差下降、实战退步」。

- 采样时为每个决策额外保存前 k 个候选（例如 k=8）的输入和锚点模型分数；
- 训练时对这些候选加相对锚点的 softmax KL 项；
- 注意存储量：每个候选 567 字节，k=8 时样本量约为现在的 9 倍，需要相应调小缓冲区或改格式。

**完成标准**：有开关，默认关闭；开和关两个运行的对比写进报告。

### 第 6 步：验收现有最强候选

**目标**：尽快让所有电脑变强。

- 目前最强的已有候选是 `ppo-mixed` 第 14 周期的小 Actor（扩大实验里四组全网络模型对它的胜率都低于 50%，见研究报告第 7.6 节）。
- 用第 2 步的验收脚本对它跑留出验收。它需要 PPO 配置（`--config`），参考 `ai/local/evaluation/evaluate-table.mjs` 的用法。

**完成标准**：验收报告写进研究报告；只有通过预定标准才宣称提升。网页部署按所有者后续的四小时授权执行，不能把部署记为验收通过。

### 第 7 步以后（按证据决定是否做）

- **种群训练（PBT）**：同时跑 2–3 个训练进程，不同学习率和温度，定期复制表现好的权重并扰动超参数。
- **对局时搜索**：关键局面抽样补全其他三家手牌，用模型模拟到局末；先在门控里比较，再考虑放进网页 Worker。
- **进还贡学习**：选项少，可以枚举后用模型评估，见改进意见第 7 节。
- **新特征**：最近 20 手出牌序列、进还贡信息、牌权归属。需要新网络结构，先用 P0 蒸馏，再继续训练。具体做法见下一节 D1。

[DouZero](https://github.com/kwai/DouZero) 是快手开源的斗地主 AI，与本仓库采用相近的方法框架：把动作也作为输入的 Q 网络、深度蒙特卡洛回报、多采样进程加一个训练进程。观察编码、游戏与网络激活并不相同；仅凭结构相似不能确定 P0 的来源，没有原始训练记录时不作来源确认。

**资料来源**：下列 DouZero 的事实核对过仓库 README、`douzero/dmc/arguments.py` 和 `douzero/dmc/models.py`；DouZero+ 与 PerfectDou 两篇论文的内容来自记忆，动手前请先查原文核实。

**2026-11-04 补充核对**：已核对上游当前提交 `718a5c920bf3361e34178a38f3b80458e176b351` 的[模型](https://github.com/kwai/DouZero/blob/718a5c920bf3361e34178a38f3b80458e176b351/douzero/dmc/models.py)、[训练参数](https://github.com/kwai/DouZero/blob/718a5c920bf3361e34178a38f3b80458e176b351/douzero/dmc/arguments.py)、[环境编码](https://github.com/kwai/DouZero/blob/718a5c920bf3361e34178a38f3b80458e176b351/douzero/env/env.py)与评测生成器。其 LSTM 隐藏维度为 128，MLP 使用 ReLU；本仓库 P0 使用 tanh，D1 为保持初始化等价应保留 P0 的原激活，不能直接照搬上游 MLP。已从 [DouZero+ 原论文摘要](https://arxiv.org/abs/2204.02558v1)核实对手建模与教练网络方向，从 [PerfectDou 原论文摘要](https://arxiv.org/abs/2203.16406v7)核实明牌训练、暗牌执行及 PPO/GAE；这不等于已核实全文的标签、损失或超参数，实施相应任务前仍需阅读全文。

**与当前进度的关系**：这些任务排在第 1 步之后。正在运行的 `gpu-main` 源码已冻结，不要为了这些任务改动它；新功能用新运行目录验证，每项都与同初始模型、同采样设置的对照运行比较，结果按 AGENTS.md 写进研究报告。第 7.8 节的 `step1-smoke` 锚点检查（18 胜 268 负 14 平）和第 7.10 节的首轮门控拒绝都说明：从 P0 继续训练可能先退步，任何新结构都必须先通过锚点检查，不能只看训练损失。

#### D1：用 LSTM 编码出牌历史（优先）

- **DouZero 的做法**：最近 15 手出牌整理成 5×162 的矩阵，送入 `LSTM(162→128)`，取最后一步输出，与局面特征拼接后进入 6 层 MLP（`dense1`～`dense5` 为 512，`dense6` 输出 1 个值）。
- **本仓库现状**：参考客户端的 `_process_action_seq()` 与 `_action_seq_list2array()` 已把最近 20 手整理成 5×216（每行 4 家 × 54），但 `prepare()` 没有使用，P0 也没有这部分输入。研究报告第 9 节把缺少序列编码列为局限。
- **要做的**：
  1. 在 `web/src/ai/encoding.mjs` 旁新增序列编码（沿用参考客户端的 20 手、5×216 排法，过牌与出完的哨兵值与现有 `replay()` 一致），并用参考 Python 实现做逐值一致性测试。
  2. 新网络 = P0 的 MLP + LSTM 分支；LSTM 输出接入第一层的投影初始化为零，使初始输出与 P0 逐位一致（写测试证明）。
  3. 样本分片增加序列特征；`learner.py`、`value_net.py` 支持新结构；导出新的 ONNX 输入，网页 Worker 与 `evaluate-table` 暂不切换。
  4. 新运行目录从 P0 等价初始化开始，与不带 LSTM 的对照运行比较门控和锚点记录。
- **完成标准**：初始等价测试通过；两组运行跑够相同训练步数；锚点和门控结果（包括负结果）写进研究报告。

#### D2：明确比较「升级分目标」和「胜率目标」

- **DouZero 的做法**：`--objective` 可选 `adp`（平均分差，默认）、`wp`（胜率）和 `logadp`，两种主要目标都发布了预训练模型。
- **本仓库对应**：这里只类比目标类型，不等同于 DouZero 的原奖励定义。`targetMatchWeight=0` 拟合单局升级分；`targetMatchWeight=1` 拟合整场胜 +3、负 −3、平 0，中间值是混合。含平局时，后一目标对应胜 1／平 0.5／负 0 的得分变换，不等于单独最大化胜局数；评测仍同时报告纯胜率、平局率和得分。
- **要做的**：把第 4 步的对照扩成四组：`targetMatchWeight` 取 0、0.5、1，加上势函数版本。主指标是整场胜率，同时报告单局升级分。
- **完成标准**：四组用同一初始模型和同样采样设置，跑够相同训练步数；按整场胜率选默认值，证据不足时保持现有默认。

#### D3：预测其他三家手牌作为辅助任务（DouZero+ 的对手建模）

- **思路**：自对弈时其他三家的真实手牌已知，可以作为监督标签。在网络上加一个辅助输出，预测队友和两家对手各自剩余的 54 类牌计数（每类 0／1／2），与 Q 值一起训练；若采用 54×2 通道，可表示计数至少为 1／至少为 2，不要求猜测不可辨认的同面物理副本 ID。这是本项目待验证的标签设计，不是已核实的 DouZero+ 原标签格式。决策输入仍然只用本人手牌和公开信息。
- **额外用处**：预测出的手牌分布可以作为第 7 步「对局时搜索」抽样补全三家手牌的依据。
- **要做的**：采样时额外保存三家的真实剩余手牌（只用于训练标签，不进入决策输入，也不进入网页）；`learner.py` 加辅助损失和权重开关，默认关闭。
- **完成标准**：有单元测试证明标签不进入决策输入；开和关两组运行的锚点、门控结果写进报告；同时报告手牌预测的准确率，但不把预测准确率当成棋力。

#### D4：固定评测牌局与基线集合

- **DouZero 的做法**：`generate_eval_data.py` 生成 10,000 局固定牌局，`evaluate.py` 可以给每个座位指定任意 AI；基线包括随机、RLCard 规则机器人和用人类数据训练的监督模型。
- **要做的**：生成一份固定的掼蛋评测牌局清单，记录种子区间和 SHA-256，放进 `ai/research/evaluation/`；基线至少包括随机合法出牌、规则机器人和 P0。可以与第 2 步的留出验收一起设计，但开发评测牌局和留出牌局必须分开。
- **完成标准**：任意两个模型文件都能用同一份牌局清单对比，输出逐种子结果和区间。

#### D5：进还贡单独建模

- **来源边界**：上游 README 链接了叫牌演示，但本次核对的标准训练源码仅列三个出牌角色模型，没有据此确认独立叫牌网络的训练实现，故不把“另训叫牌网络”写成已核实的原版事实。
- **对应**：掼蛋的进贡、还贡选项很少，适合单独的小网络或逐个枚举后用模型评估（与第 7 步的「进还贡学习」合并做）。

#### 不要照搬的

| DouZero 的做法                                  | 不照搬的原因                                                                                                                                                |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ε=0.01 均匀随机探索                             | 本仓库实测会让整场得分下降约 8 个百分点（见上文探索测量）。掼蛋一整场约 650 个决策，比斗地主一局长得多，随机打出炸弹或拆牌的代价被放大。保留 softmax T=0.02 |
| RMSprop、学习率 1e-4、梯度裁剪 40、batch 32×100 | DouZero 从零开始训练；本仓库从 P0 继续训练，且已观测到退步。保持学习率 1e-5，可另开 1e-4 的运行作对照，不直接改默认值                                       |
| 每个位置一套网络                                | 斗地主地主与农民角色不对称；掼蛋四个座位对称，共用一个网络、用特征表示局势更省数据                                                                          |
| PerfectDou 的明牌训练、暗牌执行                 | 本仓库第 4.4、7.6 节的明牌 Critic 实验在小样本下没有一致优势。等持续系统跑出规模后，再作为对照组重试                                                        |

**建议顺序**：D1 → D2（与第 4 步合并）→ D3 → D4（与第 2 步合并设计）→ D5（与第 7 步合并）。

## 已知问题与风险

| 问题                         | 位置                                        | 说明                                                                           |
| ---------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------ |
| 门控只看网络本身             | `gate.mjs`                                  | 冠军在网页完整流程里不一定更强，第 2 步的验收负责兜底                          |
| SPRT 是正态近似              | `lib.mjs` `sprt()`                          | 方差下限 0.05、至少 100 对；冒烟时用 4 对就接受过一次，所以不要调低 `minPairs` |
| 对局结果含探索               | `actors/results-*.jsonl`                    | `npm run train:status` 里的胜率只用于监控，不是评测                            |
| 每个决策等权                 | `learner.py`                                | 长比赛贡献更多样本，研究报告第 4.2 节记录过同样的限制                          |
| 进还贡是固定程序             | `ai/shared/simulation/match-simulation.mjs` | 训练和评测都用同一套规则程序                                                   |

| 客人能看到四家手牌           | `web/src/game/session.js:55`                | 与训练无关的安全问题，仍未修复                                                 |
